# Development notes

The real `VRGirlz` data folder is vendor material and is never part of this
repository, so anything that touches real assets has to be run on a machine
that has the game installed. Everything else (assembler logic, manifest
schema, the CLI plumbing) is developed and tested against the synthetic
fixture.

## Tests without vendor assets

`uv run pytest` runs entirely against `tests/fixtures/synthetic/`, a
synthetic scene generated by `scripts/make-fixture.py` in the same
JSON+NPZ shape `reader/fixture_backend.py` expects — same node names, TRS
patterns, and LOD/material/texture wiring as the real file, but tiny
procedural meshes and checker-pattern textures. Regenerate it with:

```bash
uv run python scripts/make-fixture.py
```

## glTF validation

`scripts/gltf-validator/` pins the Khronos glTF-Validator (npm
`gltf-validator`, exact version in its `package.json` and lockfile). Once,
on a machine with node:

```bash
npm ci --prefix scripts/gltf-validator
```

Then `node scripts/gltf-validator/validate.mjs <dir or .gltf> …` validates
every glTF with its buffers and images and prints one JSON report — per file
the issue counts and every error and warning, totals, a count per issue
code — exiting 1 on any error. `tests/test_gltf_validator.py` converts the
three synthetic fixtures and validates them: no errors, and no warning but
`MESH_PRIMITIVE_GENERATED_TANGENT_SPACE` (no TANGENT attribute in Ф1, see
`docs/manifest.md`). It is skipped without node, and fails with the command
above when node is there but the validator isn't installed. Real output is
validated on a real-data machine only — the same command against `out`.

`reader/unitypy_backend.py` (the only module that imports UnityPy) has no
dedicated unit tests in Ф0 — it can only be exercised against the real
file, on a real-data machine, via `vrscan scan`. `assembler.py`, `manifest.py`, and the
`cli.py` report/formatting code are backend-agnostic (`reader/backend.py`'s
`ReaderBackend` protocol) and are fully covered against the fixture.

## Serving the viewer during development

`vrscan serve <out-dir>` works with an empty (or nonexistent) `viewer/`
directory — it just 404s on `/` until the viewer is built in a later phase.
`out-dir` needs to exist; point it at any writable directory to smoke-test
the server (`--https` will drop a self-signed cert under
`<out-dir>/.vrscan/cert.pem`, reused on subsequent runs). It binds its port
itself: if another program listens on `--port` (default 8443 with
`--https`), it takes the next free one and prints it — with `--progress
jsonl`, as a `ready` event on stdout (`docs/LAUNCHER.md`).
